# Phase 0+1 on the real machine, and what the machine will let you measure

Amiga 3000, AMIX 2.1c, kernel 68060-260831-01, VA2000 in Zorro III
(the driver reports a 32704 KB framebuffer), 800x600x16.

## The headline is about the method, not the phase

**This machine's timings vary by about a factor of two between consecutive
runs of an unchanged binary, even with every test held above three
seconds.** Two passes of the same benchmark against the same server:

| test | pass 1 | pass 2 |
|------|-------:|-------:|
| fillrect10 | 27429 | 13935 |
| imagetext (chars/s) | 5063 | 3352 |
| line | 887 | 1644 |
| fillrect100 | 3220 | 4620 |

That is the `-O` build, but every build did it, in different places each
time. The saku26 demo saw the same thing from the client side -- 14, 15,
40, 46 and 47 ms/frame for one unchanged configuration -- so it is a
property of the machine, not of this benchmark.

**Nothing below a factor of two is measurable here by this method.** The
cause is not yet known; a periodic background load (the screen manager, the
disk syncer) is the obvious suspect and has not been checked.

## Phase 1: no measurable effect

An earlier version of this file reported that GNU C 2.7.2.3 was 25% slower
than 1.40.5 on small fills. **That was wrong, twice over.**

First, the test it rested on set the foreground colour before every
rectangle, so it measured GC validation rather than filling; separating the
two moved `fillrect10` from 6667 to 27000 ops/sec and put the difference in
a `gcchange` test instead. Second, once each test was made to run for at
least three seconds, the difference disappeared into the variance above:
`fillrect10` reads 27298 for the old build and 27428-27560 for the new one.

So the honest result for phase 1 is **no measurable difference** between:

- GNU C 1.40.5, `-O`
- GNU C 2.7.2.3, `-O2 -m68030`
- GNU C 2.7.2.3, `-O -m68030`

which is consistent with saku26's finding that GCC 14 `-O2` and GCC 2.7.2.3
`-O` landed within 3% of each other in bus-bound loops. Phase 1 keeps its
place because it unblocked the newer compiler and surfaced three latent
defects, not because it made anything faster.

## What is measurable: the large effects

These are ratios of 25x and up, far above the noise, and they reproduce
across every build and pass.

| | ops/sec | note |
|---|---:|---|
| `copywinwin100` | 1145-1243 | blitter path |
| `copypixwin100` | 32-35 | miCopyArea fallback |
| `copywinpix100` | 32-43 | miCopyArea fallback |

**The blitter path is around 30x the fallback**, and the fallback is what
the software cursor uses on every pointer move. Review item 2, confirmed.

`putimage101x100` runs at 20-33 ops/sec over 10100 pixels, so 0.2-0.34
Mpixel/s -- reproducing saku26's 0.26-0.35 Mpixel/s from an unrelated
client. Review item 4.

`text` runs at 3400-5250 chars/s, i.e. 190-290 us per character. Review
item 1.

## One thing worth chasing

The **pre-phase-0 server crashed** during a long text run:

    XIO: fatal IO error 130 (Software caused connection abort)
         after 67260 requests

The phase 0+1 build survived the same test twice. One crash is not
evidence, but miPolyGlyphBlt allocates a pixmap and a scratch GC per call,
so a leak there is plausible and would be worth confirming before phase 3
replaces that path anyway.
